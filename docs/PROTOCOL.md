# Controlled browser workflow protocol

The primary study crosses decision provider with waiting policy and observation mode on three independently hosted synthetic applications. Each supported condition targets three independent repetitions; one repetition has creation, update, and retained status transition, each followed by reload and fresh target inspection. Six primary conditions are executable. Two Jev combined-image conditions are retained as unsupported, without substitute vision or OCR.

VM resources are fixed at four vCPUs and 8GB RAM, Chromium viewport 1440×900, America/New_York browser timezone. Run paid jobs serially. Record actual browser/model versions and the frozen code hash. Randomize conditions within application/repetition blocks using the immutable seed. Task values are identical within application/repetition blocks; records and histories are never shared between conditions.

Each operation allows 30 physical actions and 120 seconds. Wait decisions do not send input. The one-second sampling target is extended by serial API latency. API transient errors retry at most twice. The public helper makes closed-schema recommendations from current controls and supplied values; it never executes browser actions. Batch planning retains at most four independent field assignments, invalidated by structural changes, unexpected values, navigation or errors; all targets are rematched against fresh observations.

The agent has no access to fixture receipts or internal server state. After declaring completion it reloads, finds and opens the target with mutation controls excluded. Verification requires observed expected fields/status, independent server persistence, exactly one target, unchanged synthetic distractor records, and the expected last operation. False completion and duplicate creation cannot satisfy the oracle.

Failures of creation prevent update and closure from starting. Unsupported input and dependency outcomes are separate from independent failures. Rank complete successful workflows ahead of speed. Report success intervals and the actual repetition count; do not claim universal reliability or a speedup from a short failed attempt. Costs include helper and retry calls, estimated separately from invoiced billing.

The helper pilot measured about $0.064 for a three-operation contact workflow. That pilot is separate from the primary study. To fit the shared provider budget, the main study fixes assistance off; a separately named one-repetition follow-up evaluates helper and batch mechanisms. Its sample sizes must not be pooled with the three-repetition direct-model study.

Each application includes two synthetic unrelated records. The oracle compares them to an independent pre-run snapshot, making wrong-target updates and status changes observable. Target records are created independently under every condition. These fixture audits do not establish safety on arbitrary external websites.
